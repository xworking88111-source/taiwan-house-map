## 1. 舊版 ETL 找到的問題

我先把 `national_trade_final_history.rds`（2,333,894 筆）整份掃過一遍，看每個欄位實際長什麼樣子，再對照程式碼。這個步驟叫 **資料剖析（data profiling）**：先看資料，再寫規則，不要憑想像寫。

### 問題 1（嚴重）：沒有「縣市」欄位

- 政府的 CSV 檔名第一個字母代表縣市：`a_lvr_land_a.csv` = 臺北市，`e_...` = 高雄市。
- 舊版用 `map_df` 把所有檔案合併時，沒有把這個資訊存下來。
- 後果：
  - 「中正區」同時存在於臺北市和基隆市，「東區」有新竹市、嘉義市、臺中市、臺南市四個。統計時這些會混在一起。
  - 約 30 萬筆地址本身沒寫縣市（例如 `忠孝東路六段21號`），沒辦法定位。
- 修正：`read_one_season()` 從檔名取字母，對照 `city_code` 補上 `city` 欄位。

### 問題 2（嚴重）：建築完成年月有幾種格式會轉錯

實際資料的分布：

| 長度 | 筆數 | 例子 | 舊版結果 | 正確 |
|---|---|---|---|---|
| 7 碼 | 171 萬 | `0870312` | 1998 ✅ | 1998 |
| 6 碼 | 9 | `087129` | **1919** ❌（取前 2 碼 `08`） | 1998 |
| 6 碼 | — | `000000` | **1911** ❌（還通過了 ≥1900 的檢查） | NULL |
| 5 碼 | 434 | `06701` | 1978 ✅ | 1978 |
| 髒值 | 少數 | `05910-`、`066  25` | NULL（資料直接丟掉） | 1970、1977 |

新規則：
1. 先取「開頭連續的數字」：`05910-` → `05910`，`066  25` → `066`，`-450101` → 空字串。
2. 開頭是 0 或 1、長度 ≥ 3 → 前 3 碼是民國年（政府的格式會補零到 3 碼）。
3. 否則長度 ≥ 4 → 前 2 碼（沒補零的舊格式，例如 `850312`）。
4. 結果必須在「民國 1 年～今年」之間，否則設為 NULL。

交易日期：7 碼占 99.99%，另外有 6 碼 239 筆、5 碼 12 筆。民國年出現 116、117、119、120、122、190 這些未來年份，都是登錄打錯，會被「≤ 今年」擋掉。

### 問題 3（Bug）：扣車位的單價從來沒算過

```sql
WHEN include_parking = 'Tier_1' AND ...   -- 舊版
```

`include_parking` 的值只會是 `'是'` 或 `'否'`，永遠不會等於 `'Tier_1'`，所以這個分支從來沒執行過，`pure_house_unit_price_ping` 一直都等於原始單價。已改成 `'是'`。

### 問題 4：讀檔失敗會被靜默吞掉

```r
tryCatch({ read_csv(...) }, error = function(e) return(NULL))
```

某個檔案讀不到時直接回傳 NULL，你不會知道少了一個縣市。新版改成 `warning()` 印出檔名。
**原則：錯誤可以被處理，但不能被隱藏。**

### 問題 5：「預售屋」比例很高，這是正常的

清洗後約 21% 被分類成預售屋。我原本以為是 bug，查了以後發現 a 檔裡備註寫「預售屋」的有 41 萬筆。這些是「預售時簽約、完工後過戶」的交易，簽約日期本來就會早於建築完成日。分類邏輯沒有問題。

> 這也是一種重要的工作習慣：看到奇怪的數字，先查證，不要急著「修」。

### 其他改進

- 地址標準化：全形數字轉半形，「台」統一成「臺」，「巿」（U+5DFF）改成「市」。這個字和「市」肉眼看不出差別，但電腦視為不同字，原始資料裡真的有。
- 中文樓層轉數字：`十一層` → 11，`地下二層` → -2。模型需要數字才能用。
- 特殊交易關鍵字擴充：加入 `特殊關係|債權債務|瑕疵|凶宅|事故|法拍` 等。
- `套房` 獨立成一類（原本歸在「其他」）。
- 欄位名稱改用「位置」對應，不用英文標題對應。政府的英文標題大小寫不一致，但 25 季的欄位順序我逐季檢查過，完全相同。

## 2. 資料庫概念（這次用到的）

### Schema：資料庫裡的「資料夾」

```
postgres (資料庫)
├── public  (預設 schema)  ← 你舊的 5 張表在這裡，完全沒動
├── re_v2                  ← 新版全部放這裡
└── etl_test               ← 我測試用的，已刪除
```

好處：新舊版本可以同時存在，舊的不會被覆蓋，要比較或回退都很方便。

```sql
SET search_path TO re_v2, public;
-- 意思：之後寫 SELECT * FROM raw_trade，先去 re_v2 找，找不到再去 public
```

### ELT 與「分層」

| 層 | 表 | 內容 | 為什麼 |
|---|---|---|---|
| 原始層（staging / bronze） | `raw_trade` | 全部存成文字，盡量保持原貌 | 清洗規則改了，只要重跑 SQL，不用重新下載 |
| 清洗層（silver） | `real_estate_clean` | 型態正確、年份轉好、分類好 | 所有分析共用的「單一真相來源」 |
| 主題層（gold） | `fact_residential_house` 等 | 針對特定用途篩選 | 地圖、模型直接用 |

ETL 是先轉換再載入；ELT 是先載入，再在資料庫裡轉換。你的專案是 ELT：資料庫做 Transform 比 R 快，而且 SQL 是資料工程師的必備技能。

### 冪等（Idempotent）：同一支程式跑幾次，結果都一樣

```r
dbWithTransaction(con, {
  dbExecute(con, "DELETE FROM raw_trade WHERE season = $1", params = list(p))  # 先刪這一季
  dbAppendTable(con, "raw_trade", df)                                          # 再寫入這一季
})
```

如果只寫 INSERT，跑兩次資料就會重複。「先刪再寫」可以保證跑幾次都一樣。之後每週自動排程，最怕的就是重複執行把資料弄亂，所以這個性質很重要。

### 交易（Transaction）：要嘛全部成功，要嘛全部取消

上面的 `dbWithTransaction` 把 DELETE 和 INSERT 包在一起。如果 INSERT 寫到一半當機，DELETE 也會自動復原（rollback），不會出現「舊資料刪了、新資料沒進去」的狀況。銀行轉帳也是用同樣的機制。

### `$1` 參數化查詢

```r
dbExecute(con, "DELETE FROM raw_trade WHERE season = $1", params = list(p))
```

不要用 `paste0("... WHERE season = '", p, "'")` 拼字串。參數化查詢可以防止 **SQL 注入攻擊**。資料只是填進去的值，不會被當成 SQL 指令執行。

### 索引（INDEX）

就像書的目錄。`WHERE city = '高雄市'` 有索引時可以直接跳到對的位置，沒有索引就要從第一筆掃到最後一筆。

- 代價：寫入變慢、多占空間，所以只替「常被篩選或 JOIN 的欄位」建立。
- 複合索引 `(city, district)` 的順序有差：它能加速 `WHERE city=...` 和 `WHERE city=... AND district=...`，但**不能**加速只查 `district` 的情況。可以想成電話簿先依姓排、再依名排。
- `ANALYZE`：更新統計資訊，讓 PostgreSQL 知道每個欄位的資料分布，才會選對索引。

### PRIMARY KEY（主鍵）

```sql
addr_key TEXT PRIMARY KEY
```

主鍵 = 不可重複 + 不可空白 + 自動建立索引。`geo_cache` 用地址當主鍵，保證每個地址只會有一組經緯度。

### CTE（`WITH ... AS`）

`real_estate_clean` 的 SQL 用了 `WITH parsed AS (...), years AS (...), typed AS (...)`。這是把一個大查詢拆成幾個有名字的步驟：先剖析字串，再算年份，再轉型態。和 R 的 `%>%` 是同樣的思路，可讀性比巢狀子查詢好很多。

### LEFT JOIN 找「還沒處理的」

```sql
SELECT r.addr_key FROM raw_trade r
LEFT JOIN geo_cache g ON r.addr_key = g.addr_key
WHERE g.addr_key IS NULL     -- 右邊對不到 = 還沒算過經緯度
```

這是增量處理最常用的寫法，面試很常考。

## 3. 地址轉經緯度

### 問題規模

- 233 萬筆中，約 58 萬筆是純土地（地址是「XX段XX地號」），沒有門牌，不需要定位。
- 有門牌的 175 萬筆，**去掉樓層後只剩約 76 萬個不重複的建物地址**。同一棟大樓的交易共用一組座標，這個「去重複」的動作把工作量砍掉一半以上。

### 方案比較

| 方案 | 免費額度 | 76 萬筆需要多久 | 結論 |
|---|---|---|---|
| Google Geocoding API | 每月約 1 萬筆 | 6 年 | ❌ |
| TGOS 線上批次比對 | 一次 500 筆 | 1500 次手動上傳 | ❌ |
| Nominatim 公共伺服器 | 每秒 1 筆，且禁止大量批次 | 違反使用規範 | ❌ |
| 向各縣市申請門牌資料 | 收費（台北市營利用途約 23 萬） | — | ❌ |
| **OSM 道路 + 鄉鎮界線，本機比對** | 無限制 | **全台約 1 分鐘** | ✅ 採用 |

### 做法

1. 從 Geofabrik 下載台灣的 OSM 道路圖資。台灣 OSM 的路名非常完整，例如 `忠孝東路四段181巷35弄`。
2. **空間連接（spatial join）**：把每段道路的中心點放進鄉鎮界線，判斷它屬於哪個區。得到「(縣市, 區, 路名) → 座標」的對照表，共 17 萬條。
3. 把實價登錄的地址拆成多層，從最精細的開始比對：

```
臺北市松山區南京東路五段389巷5弄9號
  lane2    = 南京東路五段389巷5弄   ← 先試這個
  lane     = 南京東路五段389巷
  road_sec = 南京東路五段
  road     = 南京東路
  district = 松山區的中心點         ← 最後一道防線
```

4. 把結果存進 `geo_cache`，並記錄 `geo_level`（精準到哪一層）。之後每週只算新出現的地址。

### 結果（全台 59 萬個地址的測試）

| 精準度 | 比例 |
|---|---|
| 巷弄（lane2 / lane） | 39.5% |
| 路段（road_sec / road） | 52.7% |
| 只到行政區 | 7.7% |
| 完全無法定位 | 22 筆 |

### 座標系統（CRS）

- **EPSG:4326（WGS84 經緯度）**：單位是「度」，地圖顯示用，GPS 也是這套。
- **EPSG:3826（TWD97 二度分帶）**：單位是「公尺」，台灣官方測量用。要算距離或面積就要轉成這套，因為經緯度的 1 度在不同緯度代表的公尺數不一樣。

程式裡是先轉成 3826 計算，最後再轉回 4326 存檔。

### 誠實面對精準度

實價登錄的地址本身就有「區間化」（例如 `1～30號`），原始資料就不是精確門牌。所以路段或巷弄級的精準度，對集群地圖和區域行情是合理的。App 上可以用 `geo_level` 告訴使用者「這個點精準到路段」。**面試時主動講出資料的限制，是加分項。**

升級到門牌級的做法寫在 `new_geocode.R` 檔尾（Phase 2）。

## 4. 房價模型

### 為什麼預測「每坪單價」而不是「總價」？

總價主要由坪數決定，模型會花大部分力氣在學「坪數越大越貴」這件顯而易見的事。單價比較能反映「地段、屋齡、型態」的價值。最後再用 單價 × 坪數 = 總價。

### 為什麼取 log？

1. 房價是**右偏分布**：大部分是幾百萬到兩三千萬，少數豪宅上億。取 log 後會接近常態分布。
2. 取 log 後，模型的誤差會變成**百分比誤差**。1000 萬的房子差 10%，和 300 萬的房子差 10%，會被視為一樣嚴重。
3. 特徵的影響在現實中通常是「乘法」：屋齡多 10 年，價格約打 85 折，而不是固定少 50 萬。

### 為什麼用「時間」切訓練集和測試集？

App 的用途是「用過去的成交預測現在的價格」，所以測試集應該是**模型沒看過的未來**（最近 6 個月）。

如果隨機切，同一棟大樓同一個月的交易會同時出現在訓練集和測試集，模型等於先看過答案，這叫**資料洩漏（data leakage）**。分數會很好看，但上線後就會失準。

### 四個模型，由簡到繁

| 模型 | 概念 | 優點 | 缺點 |
|---|---|---|---|
| 0. 區域中位數 | 同區同型態的歷史中位數 | 簡單，是「至少要贏過它」的門檻 | 不考慮屋齡、坪數 |
| 1. 線性迴歸（Hedonic Pricing） | 房價 = 各特徵價值相加 | 每個係數都能解釋 | 抓不到交互作用 |
| 2. 隨機森林 | 種 300 棵決策樹，各自只看部分資料，最後取平均 | 自動抓非線性；可以給出價格區間 | 模型檔很大 |
| 3. XGBoost | 一棵接一棵種樹，每棵新樹專門修正前面猜錯的部分 | 通常最準，模型檔小 | 參數多，容易過度擬合 |

### 結果

| 模型 | MAPE | ±10% 命中率 | ±20% 命中率 |
|---|---|---|---|
| 區域中位數 | 26.2% | 28.2% | 52.3% |
| 線性迴歸 | 21.6% | 34.8% | 62.0% |
| 隨機森林 | 14.2% | 52.9% | 78.4% |
| XGBoost | 15.0% | 47.5% | 76.7% |

解讀：

- 從線性迴歸換到樹模型，誤差從 21.6% 降到 14.2%。最大的原因是**經緯度**：特徵重要度排名第一、第二是 lat、lng。樹模型可以用經緯度把地圖切成很多小塊，學到「哪一塊地比較貴」，線性迴歸做不到。
- 分建物型態看：電梯大樓 MAPE 10.6%，透天厝 21.4%。透天厝最難預測，因為土地大小、面寬、路寬差異很大，而這些資訊資料裡沒有。**這就是下一輪改進的方向。**
- XGBoost 輸給隨機森林是正常的，因為還沒調參。XGBoost 對參數比較敏感。
- 業界的自動估價模型（AVM）大約做到 ±10% 命中率 50–70%。以第一版來說，這個成績不錯。

### 線性迴歸係數怎麼讀（log 模型）

`parking = 0.037`：有車位的單價約高 e^0.037 − 1 ≈ **3.8%**（其他條件相同時）。
`parking_unknown = -0.057`：車位沒有拆價時，單價約低 5.6%。這是因為車位坪數被算進去，把單價稀釋了。模型自己學到了這個資料問題。

### 過度擬合（Overfitting）

模型把訓練資料背得太熟，連雜訊都記住了，遇到新資料就不準。程式裡防止過度擬合的設計：

- `min.node.size = 10`：每片葉子至少 10 筆，不讓樹記住個別交易。
- `subsample = 0.8`、`colsample_bytree = 0.8`：每棵樹只看部分資料和部分欄位。
- `eta = 0.05`：學習率低，每一步只修正一點點。
- **Early stopping**：另外切一個驗證集，分數連續 100 輪沒進步就停止。

### 價格區間（行情區間）

分位數隨機森林可以預測 P10、P50、P90。在測試集上，實際價格落在 P10–P90 之間的比例是 87.5%（理想值約 80%），代表區間稍微保守、偏寬。

### 下一步優化（照效益排序）

1. **鄰近成交價特徵**：附近 500 公尺內、最近 1 年同型態的成交中位數。這通常是最強的單一特徵，也是房仲估價的邏輯。
2. **周邊設施特徵**：到最近捷運站、公車站、學校、公園、市場的距離。OSM 的 `gis_osm_pois_free` 和 `gis_osm_transport_free` 就有這些資料，同一個壓縮檔裡已經包含了。你想做的「附近影響房價的設施」，可以直接拿來當模型特徵。
3. **調參**：用 grid search 或 random search 試 `max_depth`、`eta` 等參數組合。
4. **分型態建模**：透天厝和電梯大樓的定價邏輯差很多，可以分開訓練。
5. **App 版改用 XGBoost 分位數迴歸**，就不需要帶著 360MB 的隨機森林上線。

### 「AI 複檢」的建議設計

不要讓 LLM 直接猜房價。LLM 對數字不準，而且無法解釋依據。比較好的分工：

1. 模型給出單價和區間。
2. 系統從資料庫撈出 **10 筆最相似的實際成交**（附近、同型態、屋齡相近）。
3. 把「使用者輸入 + 模型結果 + 10 筆比較案例」交給 LLM，請它用白話說明：「模型估 19 萬/坪。附近 3 筆同屋齡透天成交在 17–21 萬，但你的坪數比較大，所以⋯」，並標出模型可能不準的地方。

## 8.4 模型：全量成績與兩個新技術

| 模型 | MAPE | ±10% 命中率 | ±20% 命中率 |
|---|---|---|---|
| 區域中位數 | 24.5% | 25.9% | 49.9% |
| 線性迴歸 | 23.9% | 33.1% | 58.4% |
| 隨機森林 | 14.1% | 52.0% | 79.0% |
| **XGBoost** | **13.0%** | **55.1%** | **82.1%** |

依建物型態：電梯大樓 9.1%、華廈 11.8%、公寓 16.7%、透天厝 19.5%。透天厝仍是最難預測的型態。

### 新技術 1：分位數迴歸（Quantile Regression）

一般迴歸讓「平方誤差」最小，預測的是**平均值**。分位數迴歸改用 pinball loss：

- 預測 P90 時，猜太低的懲罰是猜太高的 9 倍，所以模型會往上猜，猜到「90% 的房子都比它便宜」的位置。
- 一個 XGBoost 模型同時輸出 P10、P50、P90，檔案只有幾 MB。App 用它來取代 360MB 的隨機森林。

### 新技術 2：保形校正（Conformal Calibration）

分位數模型常常「太有自信」：P10–P90 理論上應該涵蓋 80% 的交易，實際只涵蓋了 72.5%。

校正方法：
1. 在驗證集上計算 `E = max(P10 − 真實值, 真實值 − P90)`。落在區間內時 E 是負的，跑到區間外時 E 是正的。
2. 取 E 的第 80 百分位當作加寬量 q（這次算出來是 0.0256，也就是兩端各加寬約 2.6%）。
3. 新的區間是 `[P10 − q, P90 + q]`。

結果：涵蓋率從 72.5% 提升到 **80.2%**。這個方法叫 Conformalized Quantile Regression（CQR），是近年預測區間的主流做法，而且有統計理論保證。

## 8.5 Shiny App 的設計

### 檔案結構

```
app/
├── app.R                  # 整個 App (UI + Server)
├── data/trades.rds        # 74 萬筆成交 (只有 App 需要的欄位)
├── data/towns.rds         # 368 個鄉鎮市區的界線 (簡化過)

└── models/price_model.rds # XGBoost 點估計 + 分位數模型
```

### 幾個值得學的設計

- **App 不連資料庫**：資料庫負責儲存和清洗，App 只讀匯出的精簡檔案。這叫「服務層（serving layer）」。好處是免費主機就能跑，也不用擔心資料庫被攻擊。
- **`leafletProxy`**：地圖只建立一次，之後篩選條件改變時只更新圖層，畫面不會整個閃一下重畫。
- **面量圖用「分位數」上色**：台北 80 萬/坪、台東 10 萬/坪，如果用等距切，幾乎所有區都會是同一個顏色。改成分 7 等份，每個顏色的區數量差不多。
- **成交點最多畫 3 萬筆**：再多瀏覽器會卡，所以優先顯示最近的交易。
- **`eventReactive`**：估價只在按下按鈕時才計算，不會每改一個欄位就重算一次。
- **相似成交**：同區、同型態、屋齡 ±8 年、坪數 ±40%，依距離排序。這是房仲估價的「比較法」，讓模型結果有實際案例可以對照。

### AI 複檢的設計

- AI **不自己猜價格**，只負責「解釋與檢查」：把物件條件、模型估價、10 筆相似成交交給 Claude，請它用白話說明估價是否和附近成交一致、有哪些可能偏高或偏低的因素。
- R 沒有官方的 Anthropic SDK，所以直接用 `httr::POST()` 呼叫 Messages API。
- 金鑰放在環境變數 `ANTHROPIC_API_KEY`，**絕對不能寫進程式碼**。沒有設定時，App 會自動隱藏這個按鈕。
- 我用假金鑰測過錯誤處理：API 拒絕時會顯示「AI 複檢暫時無法使用」，App 不會當掉。真正的呼叫還沒測，因為這台電腦沒有金鑰。

**為什麼 App 的筆數比資料庫少？**
1. 排除特殊交易（親友、員工、債權債務等），因為這些價格不代表市場行情。
2. 只保留交易日期在最近 5 年內的。預售交屋的「交易日期」是當初的簽約日，很多簽約日早於 5 年前，所以 45 萬筆裡只剩 21 萬筆。

**建物型態**：對照 rds 後新增了 4 種：店面、辦公商業、農舍、廠辦工廠。這幾類在最近 5 年本來就很少（店面約 170 筆）。rds 裡的 3,000 多筆店面大多是民國 108–109 年的資料，那之後政府的分類方式改了。

## 9.2 「選三民區地圖沒反應」的真正原因

1. 選了單一行政區後，面量圖只剩 1 個多邊形。
2. `colorQuantile()` 要把 1 個數值切成 7 等份，切點全部重複，程式報錯。
3. **Shiny 的觀察器（observer）一出錯，整個連線就會斷掉**，畫面變灰，之後怎麼操作都不會更新。燕巢區正常，可能是因為它被篩出來的資料剛好沒觸發這個狀況。

修正：
- 新的 `make_pal()`：切點重複時自動改用連續色階。
- 地圖繪製整段包上 `tryCatch`：真的出錯也只跳出提示，連線不會斷。
- **選了行政區就自動切換成「每棟建物」**，不用再自己切換顯示方式。
- 測試：24 個行政區（含金門、連江、蘭嶼等資料很少的區）× 4 種類別，全部通過。

## 9.3 「每棟建物一個標記」與它的限制

- 同一個 `addr_key`（同一個門牌，去掉樓層）的交易合併成一個標記。圓點越大，交易越多。點下去可以看到這棟建物最近 8 筆交易。
- 預售屋用「建案名稱」合併，一個建案一個標記。
- **限制**：地理編碼只精準到巷弄或路段，所以同一條巷子的不同建物，座標原本是同一個點。我替每棟建物加了固定的小偏移（約 ±30 公尺），讓它們散開好點選，但這**不是**實際位置。要做到真正的門牌級定位，需要 TGOS 門牌 API（要申請）或自架 Nominatim。這是之後可以升級的項目。

## 9.4 新竹市、嘉義市「沒有分區」

政府的原始資料裡，這兩個市的行政區欄直接寫「新竹市」「嘉義市」，地址也寫成「新竹市新竹市大學路…」。

解法：既然已經有經緯度，就用**空間連接**（point-in-polygon：這個點落在哪個多邊形裡）反推出東區、北區、香山區，一共補回 37,699 筆。土地和車位沒有經緯度，就畫成「整個市」一塊。

## 9.5 多人同時使用的效能

**先釐清**：App 執行時**完全不查 SQL**。資料在 App 啟動時一次載入記憶體，PostgreSQL 只負責 ETL 和資料倉儲。所以多人使用時的瓶頸是 R 的計算，而 R 是單執行緒：一個人在算，其他人就要排隊。

這次做的優化：

| 優化 | 效果 |
|---|---|
| `bindCache()` 跨使用者共用快取 | 同樣的條件只算一次。實測臺中市西屯區第 1 次 2.75 秒，第 2 次 0 秒 |
| 建物明細改成「點了才產生」 | 三民區 6,400 棟建物，原本要傳好幾 MB 的 HTML 給瀏覽器，現在只傳座標 |
| 資料依類別先切好（`split`） | 篩選時不用每次都掃 168 萬筆 |
| `debounce(300)` | 使用者連續點選時，只算最後一次 |

**快取的大陷阱（這次真的踩到了）**：`debounce` 和 `bindCache` 一起用時，快取的「鑰匙」和計算用的資料必須來自**同一個** debounce 過的值。一開始我的鑰匙用的是即時的輸入，資料用的是 debounce 過的值。切換類別的瞬間，鑰匙已經是「土地」、資料還是「成屋」，結果成屋的圖被存成土地的快取，之後所有人選土地都會看到錯的圖。改成兩者都用 `ex_in()` 之後就正確了。

**如果之後使用者真的很多**：shinyapps.io 可以調整「每個實例的 R 行程數」（多開幾個 R 平行處理）。另一個做法是把常用條件的結果事先算好存檔，部署前就先暖好快取。

## 9.6 AI 複檢改成「複製提示詞」

- **原因**：呼叫 AI API 用的是開發者自己的金鑰，使用者越多，帳單越高。免費作品集負擔不起。
- **現在的做法**：App 把「物件條件 + 模型估價 + 10 筆附近實際成交」整理成一段提示詞，使用者按「複製提示詞」，再貼到 Gemini、ChatGPT 或 Claude（App 裡有直接開啟的按鈕）。你的成本是 0，使用者還可以繼續追問。
- **設計原則不變**：AI 不憑空猜價格，而是根據我們提供的真實成交資料去「解釋與檢查」模型的結果。
- **之後想做成內建功能的話**：改用便宜的小模型（例如 Claude Haiku），再加上每人每天的使用次數上限。目前畫面上標示為 Coming soon。

# 第四輪：估價低估的 bug、完整地址輸入、圖表可讀性、模型回測

## 10.1 最重要的發現：非透天厝的估價全部低估約 25%

**現象**：高雄市三民區鼎祥街，32 年華廈，36.6 坪，模型估 14.0 萬/坪。但附近 600 公尺內條件相近的華廈，實際成交中位數是 19.2 萬/坪。

**調查過程**（遇到可疑結果時的標準做法）：
1. 先拿實際成交對照：三民區所有華廈中位數 20.1 萬/坪；屋齡 27–37 年、坪數 25–50 坪的中位數 19.1 萬/坪。確認模型真的偏低。
2. 逐一改動輸入看影響（敏感度分析）：有沒有電梯、管理、屋齡、位置，影響都不大。
3. 回頭看「訓練資料長什麼樣子」：每一筆華廈都有土地持分（例如 36.6 坪的華廈約持分 6.3 坪）。但 App 只有選透天厝才會問土地坪數，其他型態一律送 -1 給模型。
4. 驗證：把土地比例補上中位數後，模型估 **19.3 萬/坪**，和實際成交幾乎一樣。電梯大樓也從 14.1 變成 18.9 萬/坪（實際 19.8）。

**這類 bug 叫「訓練與上線不一致」（training-serving skew）**，是機器學習上線後最常見、也最難發現的問題：模型本身完全沒問題，測試誤差也正常（13%），只是上線時餵給它的資料和訓練時不一樣。這種錯誤**不會報錯**，只會默默給出錯誤的數字。

**修法**：所有型態都可以填土地持分；不知道的話，用「同縣市、同區、同型態」的土地比例中位數推估，並在畫面上說明「這個值是推估的」。

## 10.2 地址輸入：可以打完整門牌了

原本的輸入框只接受清單裡的路名，打「中山一路100號三樓」會被清掉。現在的定位流程：

1. 標準化：全形數字轉半形、台改成臺、去掉縣市區前綴、去掉樓層、「4段」改成「四段」。
2. 資料庫裡有這棟建物的成交 → 直接用這棟的位置，並列出「這棟建物的歷史成交」（例如鼎中路 220 號有 53 筆）。
3. 沒有的話 → 依序找 弄 → 巷 → 路段 → 路名。
4. 都找不到 → 行政區中心，並提醒「請確認行政區是否正確」。

畫面上新增「定位與估價依據」區塊，說明這次估價實際用的位置精準度和土地持分是怎麼來的。**透明是信任的基礎**，也是作品集裡很好的展示點。

## 10.3 圖表改得讓一般人看得懂

| 圖 | 原本的問題 | 改成 |
|---|---|---|
| 屋齡與單價 | 箱型圖的 q1、q3、median，一般人看不懂 | 「點 + 範圍線」：點是中位數，線是中間一半交易的價格範圍；滑鼠移上去會寫「屋齡 0–5 年的華廈，一半的交易在 23.9～29.5 萬/坪之間，共 N 筆」 |

| 顏色 | 店面（粉紅）和透天厝（紅）幾乎一樣 | 每種型態用色相差很大的顏色 |

**為什麼用中位數不用平均數？** 房價有極端值（一間豪宅就能把平均拉高很多）。中位數是「排在正中間那一筆」，不受極端值影響，所以更能代表一般行情。

## 10.4 模型回測（`new_model_backtest.R`）

你問「誤差太大要不要重訓、要不要用一年資料」。只看一次測試成績不夠，所以做了**滾動回測**：在 4 個不同的時間點各訓練一次，每次都只用當時之前的資料，再預測之後的 6 個月。另外比較兩件事：

- 預測 6 個月和預測 12 個月，誤差差多少（決定多久要重訓一次）。
- 用全部 4.5 年資料訓練，和只用最近 1 年訓練，哪個比較準。

結果見 `models/backtest_results.csv`，解讀方式寫在程式最後面的註解。

### 回測結果

| 切點（模型上線時間） | 測試期間 | 訓練資料 | 訓練筆數 | MAPE | ±10% 命中率 | ±20% 命中率 |
|---|---|---|---|---|---|---|
| 2024-09 | 6 個月 | 全部 | 56.7 萬 | 14.3% | 52.0% | 78.9% |
| 2025-03 | 6 個月 | 全部 | 62.4 萬 | 14.0% | 52.6% | 79.8% |
| 2025-09 | 6 個月 | 全部 | 67.6 萬 | 13.7% | 53.3% | 80.3% |
| 2026-03 | 6 個月 | 全部 | 72.9 萬 | 12.9% | 55.1% | 82.2% |
| 2025-09 | **12 個月** | 全部 | 67.6 萬 | 13.7% | 53.3% | 80.4% |
| 2026-03 | 6 個月 | **只用最近 1 年** | 10.5 萬 | 14.0% | 51.8% | 79.6% |

**解讀**：
1. **模型很穩定**：4 個不同時間點上線，MAPE 都在 12.9%～14.3% 之間，而且資料越多越準。代表 13% 的成績不是運氣。
2. **模型不容易老化**：同一個切點，預測 12 個月和 6 個月的誤差一樣（13.7%）。每週重訓已經很足夠，不需要更頻繁。
3. **舊資料有幫助**：只用最近 1 年訓練，MAPE 是 14.0%，比用全部資料的 12.9% 差。所以保留 5 年資料是對的；不建議只用 1 年。

**結論**：現在不需要重新設計模型。之前看到的大誤差（鼎祥街估 14.0）來自 App 的輸入 bug，不是模型失真。要再進步，方向是加入新特徵（附近成交價、到捷運站的距離），而不是換訓練資料的時間長度。

# 第五輪：空間特徵（交通、嫌惡設施、生活機能、附近行情）

## 11.1 新增了哪些特徵

| 類別 | 特徵 | 資料來源 |
|---|---|---|
| 軌道運輸 | 到最近的捷運站、輕軌站、台鐵站、高鐵站的距離 | OSM 車站 + 鐵路路線 |
| 其他交通 | 到最近的民用機場、公車站的距離；500 公尺內的公車站數 | OSM |
| 嫌惡設施 | 到最近的墓地、垃圾場／資源回收場、污水處理廠、工業區、軍事用地、加油站的距離 | OSM 土地使用、設施 |
| 生活機能 | 到最近的學校、公園、醫院、市場／超市的距離；500 公尺內的便利商店數 | OSM |
| 附近行情 | 附近約 500 公尺、同型態、**交易月份之前** 12 個月的成交行情；附近成交筆數 | 實價登錄本身 |

### 車站怎麼分類？
OSM 的車站只有站名，沒有標記是捷運還是台鐵（「板橋」同時有台鐵、捷運、高鐵）。所以看「車站 100 公尺內是哪一種鐵路路線」：

- 地鐵路線 → 捷運；輕軌路線 → 輕軌；台灣高速鐵路 → 高鐵；其他鐵路 → 台鐵。
- **踩到的坑**：台北段的高鐵走地下，和台鐵、捷運路線重疊，萬華、松山、西門都被當成高鐵站（算出 32 個，實際只有 12 站）。所以再加一個條件：站名必須是 12 個高鐵站之一。

### 嫌惡設施為什麼算「到邊界」的距離？
一個大工業區的中心點可能離你 2 公里，但邊界就在對面。所以面狀設施取多邊形的所有頂點，算到最近頂點的距離。

- **踩到的坑**：一開始用 `st_cast(..., "POINT")`，結果每個多邊形只取到第一個點；`st_simplify` 又把小多邊形簡化成空的，產生 NA，讓最近鄰搜尋當掉。改用 `st_coordinates()` 取出所有頂點才正確。

### 附近行情為什麼是「log 平均」不是中位數？
- 中位數沒辦法「加總」：每筆交易都要把附近幾百筆撈出來排序，76 萬筆就是好幾億次運算。
- log 平均（也就是幾何平均）可以先按「格子 × 月份」加總好，再用累計值相減，算出任意時間窗的總和。用 data.table 的 **rolling join**，76 萬筆幾秒就算完。
- 取 log 之後，一兩筆豪宅不會把平均拉很高，對極端值的敏感程度和中位數差不多。

### 最重要的原則：不能偷看答案（資料洩漏）
- 附近行情只用「交易月份**之前**」的成交，不包含同一個月和之後的月份。
- 回測時，「切點之後」的成交在上線當下還不存在，所以時間窗最多只能到切點（`cap_month`）。如果沒有這個限制，回測成績會好得不真實，上線後就會失準。

## 11.2 工程設計

| 檔案 | 角色 |
|---|---|
| `new_features.R` | 建立設施檔，替每個地址算好設施距離，存進 PostgreSQL 的 `geo_features` 表（特徵庫）。增量更新：一個地址只算一次 |
| `app/shared_features.R` | 估價時要用的函數（設施距離、單一位置的附近行情），**App 和訓練程式共用同一份**，避免再發生「訓練與上線不一致」 |
| `models/nbr_table.rds` | 最近 12 個月的成交，按「格子 × 型態」加總好的小表，App 估價時直接查 |

- **k-d tree（RANN 套件）**：56.5 萬個地址 × 17 類設施的最近距離，31 秒算完。如果暴力算「每個地址對每個設施的距離」，要算好幾千億次。
- **特徵庫（feature store）**：一個地址的設施距離只算一次存起來，訓練、回測直接 JOIN 使用，每週更新時只算新地址。這是業界常見的機器學習資料工程設計。

| 測試期 | 整體 v1→v2 | 透天厝 | 電梯大樓 | 華廈 | 公寓 |

| 2025-03 起 6 個月 | 14.2→13.6% | 21.3→20.0% | 10.0→9.7% | 12.9→12.4% | 15.8→15.5% |
| 2025-09 起 6 個月 | 13.8→13.1% | 19.9→18.8% | 9.7→9.2% | 13.7→12.7% | 15.7→15.3% |
| 2025-09 起 12 個月 | 13.6→13.1% | 19.9→18.9% | 9.6→9.3% | 13.0→12.5% | 16.2→15.9% |

**解讀**：
- 5 個測試期裡有 4 個進步，表示是穩定的改善，不是運氣。
- **電梯大樓已經穩定在 10% 以內**（最新一期 8.7%）。
- 透天厝改善了約 1.2 個百分點，但仍在 18% 左右，是拉高整體誤差的主因。

**為什麼透天厝特別難？** 透天厝的價格大部分來自「土地」，而影響土地價值的關鍵資訊，像是面寬、臨路寬度、是否為邊間、能不能做店面、建物是否增建，實價登錄裡都沒有。這是資料本身的限制，不是模型的問題。

### v2 正式模型（全量資料）

| 型態 | v1 → v2 測試誤差 |
|---|---|
| 整體 | 13.0% → **12.3%** |
| 電梯大樓 | 9.1% → **8.7%** ✅ 10% 以內 |
| 華廈 | 11.7% → **11.3%** |
| 公寓 | 16.7% → **16.0%** |
| 透天厝 | 19.4% → **18.3%** |

價格區間（P10～P90）的實際涵蓋率是 79.2%，接近 80% 的目標。

**又一個 data.table 陷阱**：`lookup_nbr()` 裡的變數叫 `cx`，表格也有一個欄位叫 `cx`。傳進 data.table 時，`tbl[tbl$cx %in% (cx - 1):(cx + 1), ]` 裡的 `cx` 會被當成「欄位」，結果整張表都被選到，示範估價算出不合理的 33.1 萬。修法是改用不會撞名的變數 `qx`、`qy`，並先轉成 data.frame。

# 第六輪：屋況與產權的價值區間

## 12.1 想法

模型看不到裝潢、屋況，所以它的估價代表「一般屋況」的行情。你的想法是：先給出一般屋況的估值，再讓使用者選擇屋況和產權情況，價格跟著調整，形成「價值區間」的概念。

關鍵在於：**調整幅度要從資料量出來，不能憑感覺給。**

## 12.2 做法（`new_condition_adjust.R`）

1. **從備註文字萃取條件**（非結構化資料 → 特徵）：含裝潢、屋況不佳、帶租約、凶宅、海砂／輻射屋。
2. **交叉預測（out-of-fold）**：資料分 3 份，每次用 2 份訓練、預測第 3 份。每筆交易的預測都來自「沒看過它」的模型。分份以建物為單位，同一棟的交易在同一份，避免洩漏。
3. **殘差分析**：殘差 = 實際價格 ÷ 模型預測 − 1。例如「含裝潢」組的殘差中位數，就代表裝潢讓價格比一般行情高多少。
4. **扣掉基準**：減去「備註沒有任何條件」那組的殘差。
5. **樣本不足就不給數字**：少於 30 筆的條件改用各型態合併的結果；合併後還是不到 30 筆，就不調整價格，只顯示警告。

## 12.3 結果

| 條件 | 電梯大樓 | 華廈 | 公寓 | 透天厝 | 樣本數 |
|---|---|---|---|---|---|
| 含裝潢／家具家電 | +2.7% | +4.5% | +8.7% | +5.0% | 24,798 |
| 屋況不佳 | −1.9% | −3.6% | −13.1% | −2.3% | 615 |
| 帶租約 | +0.1% | +0.2% | +0.9% | +4.5% | 3,820 |
| 凶宅 | −37.8%* | −37.8%* | −37.8%* | −40.1% | 72 |
| 海砂／輻射屋 | 樣本不足 | | | | 16 |

\* 該型態樣本少於 30 筆，採各型態合併的結果。

**解讀**：
- 公寓對屋況最敏感（裝潢 +8.7%、屋況不佳 −13.1%）。合理，因為公寓普遍老舊，有沒有整修差很多。
- 電梯大樓對屋況最不敏感（±3% 以內）。大樓的價格主要由社區和地段決定，個別屋況的影響比較小。
- 透天厝帶租約 +4.5%：可能是有店面出租的透天，租金收益讓價格比較高。

## 12.4 這次差點犯的大錯：制式免責條款

第一次跑的結果，凶宅只有 −7%，和一般認知的 −20%～−40% 差很多。去看備註原文才發現：

> 「…惟若重大瑕疵除外如：非自然身故、輻射屋、海砂屋…」

這是買賣契約的**制式免責條款**，意思是「如果是凶宅，賣方還是要負責」，**並不代表這間是凶宅**。457 筆「凶宅」裡，大部分都是這種。排除「除外、不負、擔保、保固、不論、包括但不限」等法律用語後，真正的凶宅剩 72 筆，影響變成 −38%，才符合常理。

**教訓**：從文字萃取特徵時，關鍵字比對很容易被否定句和制式條款騙。一定要抽樣看原文，確認抓到的是你想要的意思。這也是文字探勘（text mining）最常見的陷阱。

## 12.5 App 的呈現

- 側邊欄新增「屋況」（需大整修／一般屋況／有裝潢）和「特殊情況」（帶租約／凶宅／海砂屋）。
- 改變選項時，估價**即時更新**，不用重按估價。模型只在按按鈕時算一次，屋況調整只是乘上係數。
- 新卡片「屋況與產權對價格的影響」：長條圖並列 3 種屋況下的總價，就是「同一間房子、不同屋況、不同價值」的價值區間。
- 每個調整都註明依據幾筆實際成交。樣本不足的條件用紅字提醒，請使用者另外請專業估價。
- 「毛胚」原本也規劃成選項，但成屋裡只有 2 筆（毛胚屋大多是預售屋交屋），量不出可信的結果，所以拿掉了。
