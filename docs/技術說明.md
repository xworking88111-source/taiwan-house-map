# 技術說明

這份文件說明專案的設計決策、驗證方法，以及遇到的問題和解法。功能介紹與執行方式見 [README](../README.md)。

## 1. 系統架構

```
內政部實價登錄 (季 ZIP，20 季)  +  OpenStreetMap  +  鄉鎮界線
        │  new_All_data_ETL.R        new_geocode.R        new_features.R
        ▼
PostgreSQL (schema re_v2)
  raw_trade / raw_presale ─SQL 清洗→ real_estate_clean ─→ fact_residential_house …
  geo_cache (地址 → 座標)          geo_features (地址 → 21 個空間特徵，特徵庫)
        │  new_data_checks.R (12 條資料品質規則)
        ▼
R/model_lib.R (共用函式庫) → new_model_training.R (XGBoost + 分位數迴歸 + 保形校正 + 跳動檢查)
        │  new_export_app_data.R
        ▼
app/ (Shiny) ── tests/serving_consistency.R ──→ shinyapps.io
```

每週由 GitHub Actions 自動執行：事前檢查 → 建置 (測試 → ETL → 資料品質 → 訓練 → 匯出) → 部署 (一致性測試 → 上線)。

## 2. 資料工程

| 設計 | 做法與理由 |
|---|---|
| ELT 分層 | 原始資料先原樣載入 (`raw_*`)，在資料庫裡用 SQL 清洗成 `real_estate_clean`，再切成各類事實表。轉換邏輯都在 SQL，可以在資料庫裡直接驗證 |
| 冪等 (idempotent) 載入 | 以「季」為單位，在交易 (transaction) 裡先刪後寫；重跑不會重複，中途失敗會整批回滾。只保留最近 20 季 |
| 免費離線地理編碼 | 56.5 萬個地址，用 OSM 道路 + 鄉鎮界線比對 (弄 → 巷 → 路段 → 路)，記錄精準度等級；結果存在 `geo_cache`，每週只處理新地址 |
| 特徵庫 | 每個地址的 21 個空間特徵 (到捷運、台鐵、高鐵、機場、嫌惡設施、學校的距離等) 只算一次，存在 `geo_features`；k-d tree 最近鄰搜尋 |
| 資料品質檢查 | 12 條 SQL 規則：完整性 (20 季、22 縣市、最新一季筆數)、唯一性、有效性、關聯完整性。error 級失敗就停止訓練與部署，結果寫進 `dq_results` 留歷史 |

**修過的資料問題**：「台 / 臺」「巿 / 市」不一致、新竹市與嘉義市的原始資料沒有行政區 (用座標做空間連接反推)、112S3 起 b 檔欄位改版。

## 3. 資料定義的驗證

使用者實測一筆鳳山大樓，模型估 11.7 萬/坪，附近同屋齡成交卻是 17～18 萬/坪。我先回到原始資料的官方定義檢查，而不是直接改模型。

**官方規則** (內政部不動產交易實價查詢服務網)：車位價格「和」面積都有提供時，單價 = (總價 − 車位價) ÷ (建物移轉面積 − 車位面積)；否則單價 = 總價 ÷ 建物移轉面積，車位混在裡面。

| 檢查 | 結果 |
|---|---|
| 我算的單價 vs 政府公布的單價 (34 萬筆大樓) | 價格面積都有提供的那類 100% 相同；但「只有車位價格、沒有面積」那類，舊算法 (總價 − 車位價) ÷ 含車位的面積 **低估約 24%** → 改用政府公布的值 |
| 面積組成 (主建物 + 附屬 + 陽台 + 車位 ≤ 總面積) | 99.5% 以上成立；大樓推算公設比中位數 32% |
| 權狀坪數的定義 | 建物移轉面積 − 車位面積 = **含公設、不含車位** |
| 車位沒有完整拆價的比例 | 大樓 44%、華廈 35%；同縣市同屋齡比較，單價偏低 13～24% |

那筆 11.7 萬/坪的原因是輸入的土地持分只有 3.2%。高雄 25～45 年的大樓中，土地比例 < 2.5% 的 305 筆成交有 209 筆土地為 0，備註多為「地上權」「土地向市府承租」，單價中位數 10.4 萬/坪。模型學到的是真實存在的現象，但分不出「土地少的一般房子」和「地上權房子」。

**修正**：ETL 改用官方單價、「車位不明」標記涵蓋價格或面積缺一的情況；網站的坪數欄位說明清楚、含車位時總價加上同區車位行情、土地比例超出範圍時警告、新增「地上權」選項、每筆估價顯示拆解 (SHAP：每一類因素讓價格加減多少 %)。

## 4. 模型

**目標與評估**：預測 log(每坪單價)，誤差就是百分比誤差。測試集是最近 6 個月 (時間切分，不隨機切，避免同一棟同一月的成交同時出現在訓練和測試)。永遠先比基準模型 (同區同型態中位數：MAPE 24.5%)。

**特徵 (49 個)**：基本屬性、21 個空間特徵、附近行情 (250 公尺格子 × 周圍 9 格、交易月份之前 12 個月)、同棟歷史成交 (之前 36 個月)、臨路等級 (巷弄深度、OSM 道路等級、到主要道路距離)、都市土地使用分區、主建物比例 (公設比)。所有「看過去」的特徵都只用交易月份之前的資料，回測時最多看到切點 (防資料洩漏)。

**價格區間**：XGBoost 分位數迴歸 (P10 / P50 / P90) + 保形校正 (Conformalized Quantile Regression)，P10～P90 實際涵蓋率 79.9% (目標 80%)。

**實驗紀錄** (`experiments/`、`models/experiments.csv`)：每個想法都用同一份資料、同一個測試期、同種子和基準比較，一次只改一件事。

| 實驗 | 結果 | 決定 |
|---|---|---|
| 01 穩定性：多模型平均 | 重訓時估價跳動 > 10% 的房子 6.5% → 0.7%，但 MAPE +0.4pp | ✗ 準確度優先，改用固定排序 + 種子 |
| 02 同棟歷史成交 | 有同棟紀錄的透天 16.5% → 14.6% | ✓ |
| 03 臨路等級 | 弄內透天 16.0% → 14.7% | ✓ |
| 04 附近地價 | 無改善 (資訊已包含在附近行情) | ✗ |
| 05 資料庫裡還沒用的欄位 | 全加 11.88% → 11.77%；逐一拿掉 (ablation) 發現主要用途、建材拿掉反而變好 → 只留使用分區、主建物比例 (11.77%，透天 17.45% → 17.20%) | ✓ 只留有用的 2 個 |
| 06 車位沒拆價的成交怎麼處理 | 照樣訓練 13.01% / 用車位行情還原 13.03% / 排除 13.13% | ✓ 照樣訓練，靠「車位不明」特徵修正 |

**改進是不是運氣？** 4 個時間點的滾動回測，加上以建物為單位的配對 bootstrap (同一棟的成交高度相關，逐筆抽樣會讓區間假性變窄)：v3 每一期都比 v2 好 0.32～0.43 個百分點，95% 信賴區間全部大於 0。

**目前成績**：MAPE 11.9%、中位數誤差約 8%；大樓 8.5%、華廈 11.2%、公寓 15.8%、透天 17.5%。透天最難：價值大多在土地，面寬、臨路寬度、增建等資訊實價登錄沒有。

## 5. 穩定性與監控

**估價跳動 13% 的根本原因**：同一份資料重訓，同一間房子估價可以差 13%。追查到兩個原因：
1. XGBoost 每棵樹隨機抽 80% 資料和欄位 → 固定種子
2. **SQL 沒有 `ORDER BY`**：資料庫不保證回傳順序，順序一變，固定種子抽到的也是不同的房子 → 加上固定排序

修正後同資料重訓結果完全一致 (重構前後的模型差距 0.0%)。

**跳動檢查 (drift check)**：每次重訓後，用新模型重估上一版估過的 5,000 間房子；差距中位數 > 5% 就停止部署，網站繼續用上一版。正常的行情變化約 1～3%。

## 6. 品質保證

| 機制 | 內容 |
|---|---|
| 自動化測試 (testthat 45 項、pytest 7 項) | 防資料洩漏 (同月份不能算)、時間窗邊界、地址解析、類別編號固定；用「逐筆暴力計算」的參考實作比對快速演算法 |
| 訓練與網站一致性測試 | 300 筆真實成交，分別用訓練和網站的程式算 49 個特徵、逐欄比對，不一致 > 2% 就不部署 |
| 反向測試 | 每個檢查都故意弄壞一次，確認真的會擋：植入資料洩漏 bug → 7 項測試失敗；模擬缺一季、重複匯入 → 資料品質擋下；模擬模型異常 → 跳動檢查擋下 |

**一致性測試抓到的 3 個問題** (都不會報錯，只會讓估價悄悄不準)：
1. 地圖顯示用的座標加了 ±30 公尺抖動，估價誤用了這個座標 → 另存真實座標給估價
2. 網站對透天的總樓層一律給缺值，訓練資料 97% 有值 → 透天也要輸入總樓層
3. 同棟歷史 8% 對不上：門牌含村里時找不到、多算了「年份不明成屋」、不知道離群值門檻 → 篩選條件與門檻和訓練共用

**重構時抓到的 bug**：data.table 非等值連接 (non-equi join) 的 `j` 裡直接寫 `hm`，拿到的不是每筆成交的月份，要寫 `x.hm`。原本的測試資料每棟只有 1 筆舊成交，剛好看不出來 → 補上多筆的回歸測試。

## 7. 自動化與部署

- **三段式流程**：事前檢查 (2 分鐘，金鑰、套件、部署清單) → 建置 (35 分鐘) → 部署 (5 分鐘)，用 artifact 傳遞。只改網站畫面時，用 deploy-only 拿上一次的建置結果重新部署。
- **可重現性**：建置固定 R 4.6.1 + Posit Package Manager 固定日期快照；Python 套件寫死版本；SQL 固定排序 + XGBoost 固定種子。
- **快取**：季資料 ZIP 和 OSM 圖資、跳動檢查的參考檔放在快取，失敗時也照樣存檔。

**第一次上雲端失敗 9 次的教訓**：套件來源標記 (`any::` → `Source=any`)、環境變數覆蓋 renv 的套件庫設定、YAML 多行區塊裡的 `#` 被當成內容、乾淨環境缺資料夾…。之後的做法：**先在本機重現問題、在乾淨的資料夾預演，確認後只推一次**；並把最容易失敗的檢查移到流程最前面 (fail fast)，同類問題 3 分鐘內就會被發現，而不是跑完 30 分鐘才失敗。

## 8. Python 版

核心模型 (讀資料、特徵工程、XGBoost、評分) 用 pandas 重新實作，和 R 版逐項對照：清理後筆數相同 (763,085)、MAPE 一致。工具對照：data.table rolling join ↔ `pandas.merge_asof`、RANN ↔ `scipy.cKDTree`、sf ↔ `geopandas`、testthat ↔ `pytest`。

## 9. 已知限制與下一步

- 只估「成屋」：預售屋定價看建案與建商，土地交易只有地號、無法精準定位，需要各自的模型
- 實價登錄沒有面寬、臨路寬度、屋況、裝潢 → 老透天的誤差有一部分是資料的上限
- 每週在雲端從零重建資料庫 (約 35 分鐘)；改成持久化的雲端資料庫 + 真正的增量更新，是資料工程上的下一步
